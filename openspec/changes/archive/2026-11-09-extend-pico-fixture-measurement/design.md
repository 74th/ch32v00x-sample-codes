# Design

## Context

動機は `proposal.md` を参照。今の治具の作り（`hardware/pico-tester/`）で、設計に関わる点は次のとおり。

- コマンドは1行ずつ受けて、1つずつ最後まで実行する（`protocol.c`）。実行中は次のコマンドを受けない。
- `GPIO_PULSE` は `capture_pulse()` で `gpio_get()` と `time_us_64()` をループで読む（1 µs 単位、ループの間に USB の接続確認も入る）。
- `UART_XFER` は Pico のハードウェア UART（DUT 側は uart1、GP8 送信／GP9 受信）を使い、最大 32 バイト、ボーレートは 1200〜115200。
- PIO の使用: `spi_fixture.c` が pio0 を `SPI_SLAVE` の実行中だけ使い、`ws2812_hw.c` が pio1 を `WS2812_CAPTURE` の実行中だけ使う。`ws2812_decode.pio` は、High と Low の幅を「2 PIO サイクルで 1 カウント」で数える（125 MHz なら 16 ns）。
- 固定配線: DUT の出力は GP4〜7、GP9、GP14、GP15 など（1 kΩ 直列）、I2C は GP10/GP11（220 Ω 直列、DUT の VDD へ 4.7 kΩ のプルアップ）。
- DUT 側の期待値の根拠: HSI の精度は −2.0〜+2.0 %（006 DS、−10〜70 ℃）。SPI は ch32fun・Arduino が /64（750 kHz）、WCH SDK が /256（187.5 kHz）。I2C は ch32fun 100 kHz、WCH SDK `i2c_master` 400 kHz、Arduino の Wire の既定 100 kHz（core 1.0.6 の `Wire.cpp:92`）。

## Goals / Non-Goals

**Goals:**
- 1 µs 前後の周期を、Pico の時計基準で 16 ns 程度の分解能で測る。
- 取引のコマンドの実行中に、UART とエッジ時刻を並行して取り込む。
- 既存のコマンドと試験の動作を変えない（追加だけにする）。

**Non-Goals:**
- Pico の時計の校正、電圧・波形の品質の測定。
- 配線の変更。

## Decisions

### 1. エッジ時刻は PIO で「レベルの長さ」を数える

`ws2812_decode.pio` と同じ方式（2 PIO サイクルで 1 カウント）で、High と Low の長さを交互に数えて RX FIFO に積み、DMA でリングバッファに移す。周期は High＋Low で得る。125 MHz では 16 ns 単位で、750 kHz（1333 ns）を約 83 カウントで測れる。
代替案の「ハードウェア PWM のカウンタで立ち上がりを数える（周波数カウンタ）」は、B チャンネル（奇数の GP）にしか使えず、SCK の GP6 で使えないので採らない。CPU のポーリングは、今の `GPIO_PULSE` の問題そのものなので採らない。

### 2. バックグラウンドの取り込みは、開始・読み出し・停止のコマンドにする

例: `CAPTURE_START <kind> <pin> <params>` → `CAPTURE_READ <id> <offset> <max>` → `CAPTURE_STOP <id>`。PIO と DMA が受けるので、開始の後もメインループは他のコマンド（`I2C_SLAVE`、`SPI_SLAVE`、`I2C_MASTER`、`GPIO_DRIVE` など）を実行できる。読み出しは1行の長さに収まるよう分割し、あふれ（バッファがいっぱい）を応答に示す。
PIO のステートマシンは、バックグラウンド用に pio1 の空きを確保し、既存の `WS2812_CAPTURE` と重なったときは `CONFLICT` を返す（既存の排他の流儀）。正確なコマンド名と引数は `protocol.md` に定め、プロトコルの版を上げるかは実装時に既存の `negotiate()` の扱いに合わせて決める。

### 3. UART の受信は、PIO の UART 受信にする

ハードウェア UART は受信ピンが決まっている（uart1 の RX は GP5、GP9 など）ので、GP14（DUT の PD2）などでは受けられない。PIO の UART 受信（pico-examples の `uart_rx` と同じ方式）で、固定配線の DUT 出力のピンから選べるようにする。バッファは数 KB にする。
既存の `UART_XFER` は変えない（送受信の同時実行、パリティ、32 バイトの上限はそのまま）。ボーレートの上限の引き上げは、`UART_XFER` と新しい受信の両方で、ループバックの自己検証が通った範囲にする（目標は 460800。DUT の USART は 48 MHz/16 = 3 Mbaud まで設定できる）。

### 4. I2C のバスを Low に保つのは、GPIO のオープンドレインで行う

GP10/GP11 を GPIO として、Low の出力と入力（解放）の切り替えだけで操作する。High には駆動しない（プルアップは DUT の VDD 側にある）。保持時間の上限は `GPIO_DRIVE` と同程度（例: 2000 ms）にし、終わったら安全状態に戻す。

### 5. 自己検証は、Pico の内部ループバックで行う

エッジ時刻の測定は、Pico の PWM で既知の周期（例: 1 MHz、750 kHz、100 kHz）を出し、ループバックの配線（既存の GP16〜22 の自己検証用の組）で測る。UART は既存の LOOPBACK モードの組（GP16/17）で、新しい受信とボーレートを確かめる。I2C の保持は、DUT を外した状態か、既存の I2C の自己検証の組で確かめる。DUT の判定には、自己検証が通った能力だけを使う（既存の要件のとおり）。

### 6. 周期の許容幅は、デバイスとバスの性質から決める

- SPI の SCK と PWM: 期待値 ±3 %（HSI ±2 % に余裕を足す）。Pico の水晶の誤差は小さいが、校正していないので「未校正」と記録する。
- I2C の SCL: 立ち上がりの時間（4.7 kΩ と配線容量）とクロックストレッチで、実際の周波数は設定より低くなる。期待値の −25〜+3 % を許容幅とし、測った値を必ず記録する。許容幅は最初の実測で見直し、見直した根拠をログに残す。

### 7. ログの値は、模擬の値から計算した期待値と、文字列で比べる

SHT31 の模擬（T_RAW 0x6666、H_RAW 0x8000）は約 25.0 ℃・約 50.0 %、ADT7310 の模擬（0x0C80）は 25.0 ℃。各サンプルの出力の書式（桁数）に合わせた期待の文字列を、試験のコードで計算する。取り込めなかったとき、またはあふれたときは失敗にする。

### 8. I2C のバスエラーの試験は、観測の記録にする

書籍のサンプルにバスの復旧の処理はない（タイムアウトでエラーを表示するものがある）。試験は「保持中の DUT の出力」と「解放後に取引が戻るか」を記録し、DUT の動作では失敗にしない。治具が線を解放できなかったときだけ失敗にする。マトリクスでは観測の記録として扱い、確認済みには数えない。

## Risks / Trade-offs

- [PIO のステートマシンの不足や競合] → バックグラウンド用の SM を1つ決め、既存のコマンドとの競合は `CONFLICT` で明示する。自己検証に「競合したときの拒否」を含める。
- [1 kΩ の直列抵抗と Pico の入力容量で、エッジがなまる] → 周期（同じ向きのエッジの間隔）で判定し、High の幅は参考値として扱う。
- [I2C の実際の周波数が設定より大きく下がり、許容幅に入らない] → 最初は測った値を記録して許容幅を決め、根拠をログに残す。サンプルの問題が疑われる場合は、試験を変えずに記録して別に扱う。
- [ボーレートを上げると、1 kΩ と容量で波形が崩れる] → 自己検証と DUT の実測で通った範囲だけを能力表示に出す。
- [Pico のファームウェアの更新で既存の試験が壊れる] → 既存のコマンドは変えず、更新後に 002 と 006 で全 HIL を実行して比べる。

## Migration Plan

Pico に新しいファームウェアを書き込む前に、今のファームウェアの成果物（`hardware/pico-tester/build/` の UF2）のハッシュを記録する。問題が出たら、今の UF2 を書き戻して元に戻せるようにする。書き込み後は、AGENTS.md のとおり `discover` で再認識を待ってから試験する。

## Open Questions

- 新しいコマンドの正確な名前と応答の形式（`protocol.md` で決める。試験の作りには影響しない）。
- ボーレートの上限をどこまで上げられるか（自己検証の結果で決める）。
