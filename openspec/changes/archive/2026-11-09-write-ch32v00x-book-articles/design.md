# Design

## Context

動機と章範囲は `proposal.md` を参照。既存書籍は `articles/<章番号>-<topic>/README.md` と画像・回路図からなり、`vivliostyle.config.js` はCH32V003の全章を明示列挙している。`externals/ch32v003-book` は独立したGitリポジトリで、親では無視されている。親の `.gitmodules` に登録されているのは `externals/ch32fun` のみである。

準備済みのサンプルにはデバイス別Arduino/WCH SDKと002・006共通ch32funがある。検証結果には条件や例外があり、CH32V003原稿の型番を置換するだけでは正しい説明にならない。

## Goals / Non-Goals

**Goals:** 読者が各章の説明、対応するサンプル、両型番の配線・設定の違い、確認済み範囲を追える原稿にする。書籍単体のチェックアウトでもリンクと画像が成立する構成にする。

**Non-Goals:** 新たなハードウェア検証、未解決不具合の修正、サンプルの移管、既存CH32V003書籍の改稿、出版・配布・pushは行わない。資料整備のみなので既存workflowのspecは変更せず、delta specも作らない。

## Decisions

### 1. 共通原稿と型番別の差分を1つの章にまとめる

`articles-ch32v00x/<既存と同じ章ディレクトリ名>/README.md` を1〜15章分作る。章内は共通説明を先に置き、ピン、メモリ、クロック、ADC、リマップ、API等が異なる箇所に002/006別の表または小節を置く。既存章の題材を維持しつつ、現在のコードに合う節構成に直す。2〜15章は見出し・リンク集だけで済ませず、使い方・設定の理由・コード例・配線・制約を本文として説明する。

デバイスごとに全章を複製する案は重複が大きいため採用しない。CH32V003を共通仕様の根拠として扱わない。

### 2. 原稿の入口は専用目次にする

`articles-ch32v00x/README.md` に対象型番、章リンク、サンプルリポジトリへの入口を置く。0・16・17・18・99章のディレクトリや空原稿は作らない。章番号は既存の1〜15を維持する。1章はIC概要・入手・最小回路・開発方法を簡潔に書き、ユーザー指定の4題材を省略する。

新しいVivliostyle設定やnpm scriptsを増やす案は、本文作成に必須ではないため採用しない。既存出版設定は変更しない。

### 3. コードと証拠への参照を公開先から辿れる形にする

サンプルと検証の正本は親リポジトリに置いたまま、原稿から公開GitHub URLで参照する。執筆時の参照コミットを記録し、重要なコード引用はその版と一致させる。`../../..` で親チェックアウトへ依存するリンクは作らない。book内の章・画像には相対リンクを使う。

各章の題材とデバイス・framework・サンプル・検証記録の対応を公開可能な補助資料にまとめる。既存 `articles/` の画像・回路図は型番と配線が一致するものだけ再利用し、相違する図は新原稿配下で修正・作成する。資料本文や変換物を `xprivate/` から転記・追加しない。

### 4. 成功の範囲をコードと記録で限定する

各サンプルREADME、`PROVENANCE.md`、`hil/matrix*.json`、`okf/log/` と関連知識を照合する。ビルド成功、書き込みと読み戻し、実機での信号観測、模擬デバイスによる検証、実モジュール動作を区別する。消費電流、ADC精度、時間の精度を未測定のまま数値保証しない。

特に次を執筆レビュー項目にする（原因や全個体への一般化はしない）。

- CH32V002 Arduinoのボード設定・メモリ配置の上書きとI2C slaveの制約。
- CH32V006のPC4無信号という当該DUTでの観測、PWMのPC0代替、timer DMA判定からのPC4除外、watchdogの待ち時間。
- CH32V006F8P6/F8P7の扱いはユーザー判断・資料・実測を区別する。
- NeoPixelの波形観測と実LEDの発光、OLED/UARTのPico模擬と実物モジュールの確認を区別する。
- Sleep/Standbyの起床条件と002の起床遅延の記録を反映し、未測定の消費電流を003原稿から流用しない。
- Arduino IDE/MounRiver/PlatformIOの画面操作をCLIで検証済みと扱わず、現行の対応を確認できない手順には制約を明記する。

ビルド・flashを再実行する必要はない。必要が生じた場合もツールは親の固定 `externals/ch32fun` とラッパーを使い、book-code内のch32funやPATHのminichlinkを使わない。追加の実験は別段階として `okf/log/` に実行条件と結果を記録する。

### 5. 原稿のGit操作はbookを明示する

実装開始・終了時に両リポジトリのstatusを確認する。`git -C externals/ch32v003-book rev-parse --show-toplevel` で対象を確定し、同リポジトリの新規原稿・必要な公開補助資料だけを明示的にstageしてcommitする。無関係な既存差分は含めない。原稿のコミットIDと検証結果を完了報告に残す。親のリポジトリへのcommit、無視設定変更、bookのsubmodule登録は行わない。

## Risks / Trade-offs

- [既存記事のGUI手順やライブラリ名がそのままでは002/006に適合しない] → 現在のサンプルとツール条件に合わせ、未確認の操作は明示する。
- [参照リポジトリの更新でコード引用がずれる] → 参照版を記録し、引用箇所には固定コミットへのリンクを使う。
- [PC4等の実験上の例外が一般的な仕様に見える] → DUT条件と代替配線、未解決事項をその箇所に併記する。
- [親では原稿の変更がstatusに出ない] → book内のstatusとdiffを直接確認してcommitする。
- [原稿の整備だけでは組版を保証できない] → 今回はMarkdown、参照、図の整合性を受け入れ基準とし、PDF組版は別作業にする。
