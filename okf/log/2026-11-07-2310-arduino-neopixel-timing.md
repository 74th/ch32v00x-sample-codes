## i2c_oled: CH32V003 + 公式 1.0.6 では RAM 不足（実測と推定）

- 受信したページ 0 の先頭 `6f10504a 00000000 52190000` は、`main.bin` の先頭（アドレス 0 の Flash）と一致した。2 フレームとも同じ内容で、期待画像とは 8 ページとも違う。
- CH32V003 版のリンクマップ: `_end = 0x20000448`、`_heap_end = 0x20000640` → ヒープは 504 B。ライブラリのコンストラクタの `malloc(512)` は失敗して NULL になり、描画バッファの代わりにアドレス 0 から読んで送っている（推定。コードと受信内容の一致から）。
- RAM の大きなシンボル: `__sf`（312 B、newlib の stdio）、`__atexit0`（140 B）、`Wire`（168 B）、`Serial1`（136 B）、`_impure_data`（76 B）。サードパーティ版（GCC 8）のビルドでは `__sf` がなく、`_end = 0x20000308` でヒープは 824 B（ビルドの比較のみ。実機では試していない。実機は公式配布だけ確認する方針）。
- CH32V002（RAM 4 KB）では pass している。
- テストは CH32V003 でだけ strict な xfail にした（直れば XPASS で分かる）。マトリクスの CH32V003 は `build-only` とし、理由を記録した。スケッチは変えていない。

### 元の book-code のタイミング（CH32V003、23:10 頃、実測）

ピンだけ PC6 に変えた元のコード（LSB 先頭、nop は書籍のまま）を 2 フレーム測った:

| 項目 | 実測 |
| --- | --- |
| T0H | 288〜320 ns |
| T1H | 672〜688 ns（1 フレーム目に 1 本だけ 1792 ns。送信中に割り込みが入ったと推定） |
| T0L | 736〜1056 ns |
| T1L | 528〜544 ns |

- 目標にした規格: WS2812B データシート（LuxaLight 版など一般的な改訂）の T0H 0.4 µs、T1H 0.8 µs、T0L 0.85 µs、T1L 0.45 µs、各 ±150 ns、リセット 50 µs 以上。古い改訂には 0.35/0.9 µs など違う値のものもある（Web 検索で確認。データシート本文はリポジトリに置いていない）。
- 元のコードは T0H/T1H が規格内だが下限寄りで、バイトの切れ目の T0L が 1056 ns と上限を少し超える。CH32V002 では同じコードで T1H 1008 ns（[2026-11-07-2215](2026-11-07-2215-arduino-excluded-sketches.md)、デコーダの中央値）で、規格の上限 950 ns を超えていた。同じ nop の数でも系列によって時間が約 25% 違う。
- 送り順: 元のコード（`neopixel-arduino_core_ch32` と `neopixel-register` の両方）は `c & 0x1`、`c >>= 1` で LSB から送る。WS2812 は MSB 先頭なので、書籍の 0x20 は LED には 0x04 として届く（色のチャンネルの並びは変わらず、明るさが変わる。推定）。

### 修正（`samples_{ch32v003,ch32v002}_arduino/neopixel/neopixel.ino`、両デバイス共通のソース）

- MSB 先頭で送る（`c & 0x80`、`c <<= 1`）。
- nop の数を系列ごとの定数にした（`#if defined(CH32VM00X)` で CH32V002、それ以外は CH32V003）。`.rept` で正確な数の `c.nop` を入れる。
- 送信中は `noInterrupts()` / `interrupts()`。
- CH32V003 の調整（各回は Pico で 4 フレーム測定、実測）:

| T0H / T0L / T1H / T1L の nop | T0H | T1H | T0L | T1L |
| --- | --- | --- | --- | --- |
| 14 / 28 / 37 / 13 | 400〜432 | 816〜832 | 928〜1232 | 512〜528 |
| 14 / 24 / 37 / 8 | 432〜464 | 816〜832 | 880〜1152 | 432〜448 |
| **12 / 22 / 37 / 8**（採用） | 400〜432 | 816〜832 | 848〜1120 | 432〜448 |

- nop の数と時間は単純な比例にならない（コードの配置や Flash の待ちで変わる）ので、実測で決めた。
- 採用した値で、T0H・T1H・T1L は規格の中央 ±50 ns 以内。T0L は通常のビットで 848 ns（中央）だが、**バイトの最後のビットの後は 1104〜1120 ns で、データシートの上限 1000 ns を約 100 ns 超える**（次のバイトを読むループの処理、約 12 サイクル分）。この試験フレームではバイトの最後のビットがすべて 0 なので T0L にだけ現れる。残る差として記録する（Low の延長は WS2812 では許容されることが多いと言われるが、確認していない）。
- CH32V002 の値（T0H 9、T1H 23、T0L 21、T1L 18）は、元のコードの CH32V002 での測定（T0H 384、T1H 1008 ns）から比例で見積もっただけで、**まだ測っていない**（DUT が CH32V003 のため）。

## i2c_slave: CH32V003 で Wire の slave が SCL を Low のまま固定することがある（実測）

- Arduino の全 HIL（23:15:22）で i2c_slave が失敗した（`read_0x12` の 2 バイト読み出しで TIMEOUT）。22:32 にも同じ段階で失敗していた（そのときは PD5 の不良と重なっていた）。
- 単独で 4 回 → 2 passed / 2 failed（失敗は 5 バイト書き込みの TIMEOUT）。トランザクションの間隔を 50 ms から 300 ms に広げて 6 回 → 4 passed / 2 failed（同じ段階）。間隔の問題ではない。
- 診断（23:19 頃、一回限りのスクリプト）: 書籍のテスト master と同じ「`20` を書く → 4 バイト読む → `10 aa bb cc dd` を書く」を 30 回繰り返した。1 回目は 23 回目、2 回目は 7 回目の転送で TIMEOUT になった。その時点で **SDA は High、SCL は Low のまま**（GP10/GP11 を 1 ms 間隔で 20 点）、`I2C_PROBE` は `TIMEOUT scl_stuck`。以後は DUT をリセットするまで、どの転送も TIMEOUT。
- 判断: CH32V003 + 公式 1.0.6 の Wire の slave が、ときどき clock stretching から戻らなくなる（数十トランザクションに 1 回程度）。原因は core の I2C slave 処理と推定（`twi.c` などのソースはまだ読んでいない）。CH32V002 では 4 回とも pass で、起きていない（同じ診断は未実施）。
- 21:22 と 22:41 の pass は、たまたま止まらなかった回だったことになる。マトリクスの CH32V003 の i2c_slave を `hil-verified` から `build-only` に戻し、理由を記録した。テストは CH32V003 でだけ strict でない xfail にした（23:21:18 の実行では XPASS）。

## 追記: i2c_slave の SCL 固定の原因調査（2026-11-07 23:24〜23:32 JST、ユーザーの依頼「i2c_slave のコードを読んでみて」）

### コードの読み取り（公式 1.0.6 `libraries/Wire/src/utility/twi.c`）

- `I2C1_EV_IRQHandler` → `i2c_slave_process()`。RXNE の読み出し、STOP 検出時の `onReceive` 呼び出し、そして **TXE フラグが立っていれば `onRequest` を呼ぶ**（転送方向 TRA は見ていない。440 行目付近）。
- スケッチの `on_request` は `Wire.write` を 4 回呼び、各回が `i2c_slave_write()` になる。これは **割り込みハンドラの中で** `I2C_SendData` の後、`I2C_EVENT_SLAVE_BYTE_TRANSMITTED`（TRA|BUSY|TXE|BTF）になるまで待つループ（469〜490 行目）。抜ける条件は `GetTick()` のタイムアウトか、`I2C_GetLastEvent()` が 0（状態レジスタがすべて 0）のときだけ。
- master は最後のバイトに NACK を返すので、そのバイトでは BTF が立たず、`BYTE_TRANSMITTED` にならない。抜けるには、STOP 後に状態レジスタが 0 になるのを、このループが見る必要がある。割り込みの中なので SysTick（同じ優先度）は進まず、`GetTick()` のタイムアウトは働かないと推定する。
- `I2C1_ER_IRQHandler` は回数を数えるだけで、エラーフラグをクリアしない（ITERREN は有効）。

### 実測（一回限りの診断スクリプト、DUT は CH32V003、i2c_slave サンプル）

1. 取引の組み合わせ（23:29:55）: DUT をリセットして 150 回ずつ繰り返した。
   - 書き込みだけ（`20` → `10 aa bb cc dd`）: 2 試行とも 150 回止まらない。
   - 書き込みと読み出し（`20` → 4 バイト読み出し、間隔なし）: 2 試行とも **2 回目の読み出しで TIMEOUT**。
2. ハンドラの回数カウンタ（23:30:31）: 止まった後に minichlink で `_nCounterER1`（0x20000098）と `_nCounterEV1`（0x2000009c）を 1 回だけ読んだ（いずれも初期値 1 で、入るたびに +1）。
   - 書き込みだけの 40 トランザクション後: ER=1、EV=201。
   - 書き込みと読み出しで止まった後: ER=1、**EV=5**（4 回入った後、以降のトランザクションでは一度も入っていない）。
   - ER 割り込みは一度も入っていない（「ER 割り込みが出続ける」という最初の仮説は外れ）。
3. 止まった状態では SDA High・SCL Low のまま（前出）。

### 判断

- CPU が **EV 割り込みハンドラの中（`onRequest` → `Wire.write` → `i2c_slave_write` の待ちループ）から戻らなくなっている**と判断する（推定。EV の回数が増えなくなること、読み出しが絡むときだけ起きること、コードの構造から。PC は読んでいない）。その間は受信データを読み出せないので、次の転送で slave が SCL を引き伸ばしたままになる。
- 戻れるかどうかは、最後のバイトの NACK の後、次の転送が始まる前に、ループが「状態レジスタがすべて 0」を見られるかで決まる。そのため、間隔が短いほど止まりやすい（間隔なしなら 2 回目、50〜300 ms なら数十回に 1 回）。
- CH32V002 で起きていない理由は確かめていない（I2C の状態フラグの変わり方の違いか、たまたまかは未確認）。
- 直すなら、ハンドラの中で待たない作りにするのが筋だと考える。TRA を見て送信のときだけ TXE ごとに 1 バイトずつ送り、AF（NACK）で送信を終える形（ch32fun の `examples/i2c_slave/i2c_slave.h` と同じ方式）。この change では core を直さず、記録に留める。
- 上流（openwch/arduino_core_ch32）の issue/PR を「slave」で検索したが、同じ報告は見つからなかった（23:32 頃。slave 対応は PR #108、issue #51 は 2026-11-07 に閉じられている）。
- 診断で使った minichlink のメモリ読み出しは DUT を停止させるので、診断の最後に `minichlink -b` で再開した。`-r` を何度も使うと再起動や停止が混ざり、状態の観測には向かない（最初の試みで `msTick` が小さくなった）。
