# Arduino Core CH32 で CH32V002F4P6 を扱えるかの調査（verify-arduino-core-with-arduino-cli 6.1〜6.3）

- 作業日時: 2026-11-07 21:25〜21:28 JST（記録 21:28 頃）
- 範囲: **ソースとビルド成果物の確認のみ。書き込み・実機観測はしていない**（6.2 は書き込まない段階）。DUT は CH32V003 のまま。
- 根拠: 各供給元の core のソース（boards.txt、variants、system、リンカスクリプト）、ビルドしたリンクマップと逆アセンブル、このリポジトリの既存資料 [CH32V002 移植差分](../peripherals/ch32v002-port-differences.md)。`xprivate/` の資料本文は使っていない。

## 6.1 ボード定義と流用元

| 項目 | thirdparty 1.0.5-beta | official 1.0.6 | official-git d62c6b1 |
| --- | --- | --- | --- |
| CH32V002 を選べるボード／メニュー | なし | なし | なし |
| 同系列の定義 | `CH32VM00X_EVT`、`pnum=CH32V006K8` のみ | 同左 | 同左 |
| variants/CH32VM00X | `CH32V006K8` のみ | 同左 | 同左（diff なし） |
| `system/CH32VM00X/SRC/Ld/Link.ld` | 3 つとも同一（diff なし） | | |

- 流用元の候補は `WCH:ch32v:CH32VM00X_EVT:pnum=CH32V006K8` だけ（3 供給元とも定義は同じ）。方針どおり公式配布 1.0.6 で調べた。
- `system/CH32VM00X` のペリフェラルドライバ（`ch32v00X_*.c`）には、`GPIO_IPD_Unused()` に CH32V002 の各パッケージ（J4M6、D4U6、A4M6、F4U6、F4P6）の分岐がある。これは CH32V002/004/005/006/007 共通のドライバ。

CH32V002F4P6 と流用元 CH32V006K8 の差:

| 項目 | CH32V002F4P6 | CH32V006K8（流用元の定義） | 根拠 |
| --- | --- | --- | --- |
| Flash | 16 KB | 62 KB（boards.txt `upload.maximum_size=63488`） | `Link.ld` のコメント「CH32V002: FLASH 16K, RAM 4K」「CH32V006_CH32V007_CH32M007: 62K / 8K」、boards.txt |
| RAM | 4 KB | 8 KB（`maximum_data_size=8192`） | 同上 |
| コア／ISA | QingKe V2C | QingKe V2C（`build.mcu=QingKe-V2C`、`-march=rv32ecxw -mabi=ilp32e`） | boards.txt。V002 も同じ V2C 系列（既存資料、ch32fun の `CH32V00x` 指定） |
| パッケージ／ピン | TSSOP20: PA1, PA2, PC0〜PC7, PD0〜PD7（PD7 は NRST と共用） | QFN32: variant は PA0〜PA7, PB0〜PB6, PC0〜PC7, PD0〜PD7（31 本） | `ch32hil/devices.py` の TSSOP20 表（データシート V1.7 からの既存資料）、`variant_CH32V006K8.h` |
| 既定ピン | — | Serial TX PD5 / RX PD6、SPI PC5/PC6/PC7（SS PC4）、Wire PC1/PC2 | `variant_CH32V006K8.h`。すべて F4P6 に存在し、固定配線と同じ |
| ADC | 12 bit（既存資料） | `ADC_RESOLUTION 12` | variant、[移植差分](../peripherals/ch32v002-port-differences.md) |
| クロック | HSI 24 MHz、PLL で 48 MHz（推定: ch32fun の V002 サンプルが 48 MHz で動作した実績） | `clock=48MHz_HSI` → `SetSysClockTo_48MHZ_HSI()`（`system_ch32v00X.c`、V002〜V007 共通） | core のソース。V002 で 48 MHz 設定が通るかは未確認 |
| 起動処理 | — | `SystemInit` → `GPIO_IPD_Unused()`。0x1FFFF704 の値の `& ~0xF0` でパッケージを判別し、未使用ピンを pull-down にする。実機の CH32V002F4P6 の ID 0x00200620（[既存ログ](2026-11-07-1156-ch32v002-flash-measure.md)）は `0x00200600`（F4P6 の分岐）に一致する | `ch32v00X_gpio.c` |
| スタック／ヒープ | 4 KB RAM の内側にある必要がある | `Link.ld` の MEMORY が **62K / 8K に固定**。`.stack` は RAM 末尾の `0x20001e00`〜`0x20002000`、`_eusrstack = 0x20002000`、`_heap_end = 0x20001e00` | `Link.ld`、リンクマップ |

## 6.2 流用ビルドとリンクマップ（書き込みなし）

### (a) サイズだけを上書き（タスク記載どおり）

```
./scripts/arduino.sh compile official samples_ch32v003_arduino/blink_and_read \
  --fqbn WCH:ch32v:CH32VM00X_EVT:pnum=CH32V006K8,clock=48MHz_HSI \
  --build-property upload.maximum_size=16384 --build-property upload.maximum_data_size=4096 \
  --build-path .arduino/build/ch32v002-probe/blink_and_read
→ Sketch uses 8916 bytes (54%) ... Maximum is 16384 / Global variables use 884 bytes (21%) ... Maximum is 4096
```

リンクマップ（実測）:
- `Memory Configuration`: `FLASH 0x00000000 0x0000f800`、`RAM 0x20000000 0x00002000`（62K / 8K のまま）。
- `__FLASH_SIZE = 0x4000`、`__RAM_SIZE = 0x1000` は定義されるが、`Link.ld` のどこからも参照されていない。platform.txt はこの 2 つを `--defsym` で渡すが、**リンク時の配置には効かず、サイズ上書きで変わるのは arduino-cli のサイズ検査だけ**。design の前提（`--defsym` で Flash/RAM サイズが渡る）は、配置については成り立たなかった。
- `.text` などは 0x0000〜0x22c8（約 8.9 KB、16 KB 以内）。`.data` + `.bss` は 0x20000000〜0x20000374（4 KB 以内）。
- `.stack` は `0x20001e00`（0x200 バイト）、`_eusrstack = 0x20002000`。`handle_reset` の逆アセンブルは `la sp, _eusrstack` → **sp = 0x20002000**。CH32V002 の RAM（4 KB: 0x20000000〜0x20000FFF）の外であり、最初の関数呼び出しのスタック書き込みで RAM 外にアクセスする見込み（推定。書き込んでいない）。`_sbrk` の上限 `_heap_end = 0x20001e00` も RAM 外。

### (b) スタック・ヒープのシンボルも上書き（追加で試したもの）

`Link.ld` は `_eusrstack` と `_heap_end` を `PROVIDE` で定義しているので、リンカの `--defsym` が優先される。

```
... --build-property "compiler.c.elf.extra_flags=-Wl,--defsym=__FLASH_SIZE=16384 -Wl,--defsym=__RAM_SIZE=4096 \
      -Wl,--defsym=_eusrstack=0x20001000 -Wl,--defsym=_heap_end=0x20000e00" \
  --build-path .arduino/build/ch32v002-probe/blink_and_read_stack
```

- マップ: `_eusrstack = 0x20001000`、`_heap_end = 0x20000e00`、`PROVIDE (_eusrstack = .)` は `[!provide]`（使われない）。`handle_reset` の sp = **0x20001000**（4 KB RAM の末尾）。`__global_pointer$ = 0x200008a0`。
- 逆アセンブルの差は sp を設定する命令だけで、ほかのコードは (a) と同じ。
- `.stack` セクション（NOBITS、0x20001e00）はマップ上には残るが、中身のない予約で、ロードされない。
- Flash/RAM の上限チェックは `upload.maximum_size/maximum_data_size` の上書きで 16384 / 4096 になる（ただしこの検査はスタックの 512 B を数えない）。

### variant のピン表と周辺機能（blink_and_read の場合）

- スケッチが使うピンは PC0（出力）、PA1（入力 pull-up）、PD5（USART1 TX）。いずれも F4P6 にあり、V006K8 の variant と同じ機能に割り当てられている。
- variant が定義する F4P6 に無いピン（PA0, PA3〜PA7, PB0〜PB6）は、スケッチが使わない限り操作されない。起動時に触るのは `GPIO_IPD_Unused()` だけで、F4P6 の分岐は PA0/PA3〜7 と PB0〜6 を pull-down にする（ベンダーのコード。チップに無いピンへの設定と思われるが、F4P6 用に WCH が用意した分岐なので問題ないと推定）。
- 使われる周辺機能: GPIOA/C/D、USART1、SysTick（millis/delay）、RCC。V006 にだけあるもの（OPA など）は初期化されない（リンクマップの `.text` のシンボルで確認。推定を含む）。

## 6.3 暫定判定

| 判定の候補 | 結論 |
| --- | --- |
| そのまま対応 | **該当しない**。3 供給元とも CH32V002 のボード定義はない |
| 流用（V006K8 + サイズ上書きのみ） | **不可の見込み**。スタックとヒープの上限が V002 の RAM の外になる（6.2 (a)） |
| 流用（V006K8 + サイズ上書き + `_eusrstack`/`_heap_end` の `--defsym`） | **流用で動作見込み**（暫定）。リンク結果は V002 の 16 KB / 4 KB に収まる。クロック・起動処理・ピンは CH32V002〜007 共通のソースで、F4P6 の分岐もある。ただしビルド成果物の確認だけで、書き込み・実機観測はしていない |
| 独自定義が必要 | 上の build-property の回避を「流用」とみなさない場合はこちら。CH32V002 用の pnum（Link.ld の MEMORY を 16K/4K にする ldscript）を持つ out-of-tree のボード定義になる。design の Non-Goal のため、この change では作らない |

- 方針として公式配布（1.0.6）を使う前提で調べた。thirdparty と official-git も CH32VM00X の定義（boards.txt の pnum、variants、Link.ld）は同じ。
- 書き込みを試すか（6.4）、独自定義の別 change にするかは、ユーザーの判断を仰ぐ。書き込みには CH32V003 から CH32V002 への差し替え（手作業）が必要。

## 未確認

- CH32V002 での実際の起動、48 MHz の設定、Serial の baud 精度、GPIO 動作（すべて書き込みが必要）。
- `.stack` のマップ上の位置が残ることの副作用（中身のない予約だが、ツールによっては警告になりうる）。
- CH32V002 の Flash 書き込みと readback（固定 minichlink の CH32V002 での実績はあるが、Arduino の成果物では未実施）。
