## 実施内容と結果

### 1.1 資料照合
- V006 データシート V2.0（PDF p.1–2、p.14–24）、CH32V00X RM V1.5 を読み、[差分表](../peripherals/ch32v006-port-differences.md) を作成した。本文は引用せず事実とページのみ。
- **F8P6 は V2.0 の製品表に無く、載っている TSSOP20 品は F8P7**（資料確認）。既存の [型番メモ](../devices/ch32v006-tssop20-part-number.md) と一致。F8P7 のピン定義は V002F4P6 の `_TSSOP20` と全 20 ピン同一（資料確認）。F8P6 実物のピン互換は未確認。
- ch32fun.mk の `-march` は V002 と V006 で同じ（`rv32ec_zmmul`、`-DCH32V00x=1`）。ツールの選択であり、実機での動作確認ではない。
- 12 サンプルの再利用判定: A=10 件、B=2 件（adc: ADC_CLK_MODE の差、sleep_wake: 低消費電力モード）。

### 2.1/2.2 ターゲット別 build
- `samples_ch32v002_ch32fun/target.mk`・`target-post.mk` を追加し、全 12 の Makefile から include した。固定 submodule は未変更。出力は `build/<target>/`、生成 LD は `build/<target>/generated.ld`。直接 make の既定は CH32V002。`clean` はターゲット別（固定 ch32fun.mk に `clean` は無く `cv_clean` のみ）。設定（`TARGET_MCU` と `EXTRA_CFLAGS`）を記録した `config.stamp` で変更時に ELF を再生成する。
- 実行コマンド: `make -C samples_ch32v002_ch32fun/<sample> build PREFIX=riscv64-unknown-elf TARGET_MCU=<CH32V002|CH32V006>`（全 12 サンプル×2）。結果: 全 24 件 build 成功。リンクメモリ表示は CH32V002: FLASH 16 KB／RAM 4 KB、CH32V006: FLASH 62 KB／RAM 8 KB（例: blink_and_read は FLASH 1068 B）。CH32V002 の blink_and_read は移行前の成果物とバイト一致（`cmp`）。両ターゲットの .bin は同サイズで内容は異なる。
- `TARGET_MCU=CH32V003` は `target.mk` が `error` で拒否（実測）。
- 002→006→002 を clean なしで連続 build（全 12 サンプル）: 002/006 の `main.bin` の SHA-256 先頭 10 桁は全サンプルで 2 回目も変化せず、他ターゲットの成果物を壊さない。
- ssd1306_i2c: `HELPER_CLOCK` なし→`=1`→なしで、CH32V006 の成果物が e7497b23c0db → 5f32cb5e25d0 → e7497b23c0db と切り替わり、CH32V002 の成果物（49e9b3dcc4d2）は不変（実測）。
- blink_and_read の起動表示を `blink_and_read CH32V002 started` から `blink_and_read started`（CH32V003 サンプルと同表記）にした。実機での起動ログ照合はしていない。
- 副次的な発見（記録）: 従来の HIL `Dut.build()` が `make clean` を呼んでいたが、固定 ch32fun.mk に `clean` ターゲットが無く、戻り値を見ていなかったため `make_args` のあるビルドでの事前 clean は実際には失敗していた。`target.mk` の `clean` と `config.stamp` で CH32V002/006 では解消。CH32V003・Arduino・WCH 側は未変更（本 change の範囲外）。

### 2.3/3.1/3.3/3.4/3.5 HIL 側
- `ch32hil/devices.py`: `Device.fun_root`（共有ソースのルート）と `per_target_build`・`artifact()` を追加。`ch32v006` を追加（part `CH32V006F8P6`、識別 `0x006`、物理ピンは F8P7 定義の仮置き）。`Dut` が `TARGET_MCU` を渡し、成果物を `build/<device>/main.bin` に解決する。CH32V003・Arduino・WCH のパスと既定動作は不変。
- `hil/configs/ch32v006_gpio_blink.json`、`hil/matrix_ch32v006.json`（13 行。実測前なので `build-only` と `excluded`、`hil-verified` は 0 件。CH32V002 の結果は転記していない）。
- `Run` が `Dut` を検出し、結果 `meta.dut` に device・part・framework・build_target・source_dir・artifact・artifact_sha256・variant・chip_id を記録。Pico 再列挙待ち・cleanup 条件は未変更（テストも未変更で通過）。
- 期待値生成（SSD1306 scene・WS2812 色）は CH32V003 サンプルを参照のまま。003/002/006 の各サンプルディレクトリが同じ scene.h・色を持つことを単体テストで確認。

### 3.2 スクリプト
- `scripts/ch32fun.sh` に `ch32v006` を追加（成果物・`TARGET_MCU`・識別値上位 `0x006` の事前照合・検出名の完全一致・全量 readback 照合）。ch32v002 は従来どおり（readback なし）。テスト用の `CH32FUN_TEST_MINICHLINK` で模擬プログラマに差し替える（通常は未設定。固定 submodule の minichlink を使う）。
- 模擬試験（`tests/unit/test_ch32fun_script.py`、`tests/unit/test_devices.py`）: 正常、002/003 識別値、読取不能、プログラマ異常、未接続、切り詰め、書込時の 002 検出、`Image written.` なし、書込失敗、readback 不一致（偽成功）、成果物欠落、002 選択で 006 接続。識別値不一致・未接続系はいずれも書き込み（`-w`）が呼ばれないことを確認。識別値の例は合成値（実測ではない）。
